## Implemented interface

`src/northstar_atlas/embeddings.py` uses only the Python standard library:

- `EmbeddingProvider` is a `Protocol` with `model`, `embed_documents(texts)`, and
  `embed_query(text)`. Providers satisfy it through their methods; no inheritance
  or plugin registry is required. Document outputs must match input order.
- `EmbeddingModel` records model ID, revision (or explicit `None` when unavailable),
  positive dimension, and declared normalization (`none` or `l2`). It is frozen.
- `embed_chunks(chunks, provider)` returns one `EmbeddedChunk` per input, preserving
  input order and the original immutable `PolicyChunk`. All source metadata,
  citation information, text, and chunk IDs therefore remain available.
- `embed_query(text, provider)` calls the provider's query-specific method and
  returns an `EmbeddedQuery` carrying the same model descriptor. It does not
  retain the query text in the result.
- `validate_vector(vector, dimension=...)` checks length, real numeric coordinates,
  finite values, and a finite nonzero norm, then copies the vector into a tuple
  of floats. Booleans, numeric strings, zero vectors, and NaN/infinity are rejected.

L2-normalization claims are checked with a small floating-point tolerance; vectors
are not silently normalized or otherwise changed. Duplicate chunk IDs, blank
inputs, wrong batch counts, and a provider changing model metadata during a call
are rejected. Empty chunk batches do not invoke inference. No partial list is
returned when any output is invalid.

`ProviderError` identifies the failed operation and exception type without
including the provider's raw error text or query/chunk content. Expected vector
validation errors identify the failing position. Default result representations
omit full vectors and chunk content. There are no retries, file writes, model
loads, or network operations in this component.

The wrapper cannot detect an adapter that silently reorders otherwise valid
vectors or truncates text internally. Those are explicit adapter contracts and
must be tested during real integration. Model-specific prompts, pooling, batching,
token counting, and device selection belong to the adapter, not this core.

`src/northstar_atlas/local_embeddings.py` implements `MiniLMProvider` against the
existing interface. It loads only the pinned local snapshot, uses Safetensors,
disables remote code and implicit account-token use, and performs CPU float32
encoding with two Torch threads and batch size 8. It uses the model's configured
mean pooling and L2 normalization. Document and query encoding use the same
weights and no added prompts. `token_counts()` includes special tokens, disables
truncation, and matches the encoder's surrounding-whitespace stripping.
`check_inputs()` rejects the whole batch before encoding if any input exceeds
256 tokens. The adapter does not rewrite policy chunks or their citation metadata.

HF, Torch, Sentence Transformers, and generic caches are set under the supplied
project's `.local/` before lazy third-party imports. Snapshot files, blob-directory
symlinks, and cache paths are checked against the project boundary. A missing model
fails with an explicit download instruction; inference does not fetch missing
files. This is an application workflow boundary, not OS-level filesystem isolation.

The CLI has separate `download` and `inspect` commands. Download is an explicit
network action restricted to the approved ten model files. Inspect sets offline
mode, scans token lengths for the selected corpus mode, and samples chunks
round-robin across documents. It never skips an oversized selected sample to
manufacture success. It validates the query and all selected chunks before
encoding any of them. Counts, IDs, dimensions, norms, timings, and warnings are
printed; full vectors and source/query text are not. Vectors are not persisted.

## Approved token-aware refinement

### Decision and implementation

Keep the M2.2 heading-aware chunks as the canonical, model-independent source
representation. Add `ingestion/refiner.py` between those chunks and the existing
embedding interface. No loader, canonical chunker, embedding adapter, policy,
manifest, dependency, or evaluation-label changes were needed.

`refine_chunks(originals, provider)` uses the installed `MiniLMProvider.token_counts`
and its 256-token limit, including special tokens. Only oversized originals are
refined. The other 126 chunks pass through as the same objects with unchanged
IDs and text. Original chunks are immutable and remain available to compare
other embedding models later.

`RefinedPolicyChunk` extends `PolicyChunk`, so the unchanged `embed_chunks` function
retains its extra provenance along with its vector. Document identity, version,
status, source hash, citation fields, and other metadata are copied unchanged.
The inherited `chunk_index` remains the canonical index; `refinement_index` orders
children. The original ID, model descriptor, budget, and refinement algorithm
version are explicit fields.

The refined ID has a separate `refined:token-context-v1:` namespace. Its SHA-256
identity includes original ID/source hash, model ID/revision, budget, position,
source/context spans, and rendered text. Changed sources, models, or refinement
decisions produce different IDs. Later storage should replace the complete old
generation for a document; generating new IDs alone does not delete stale vectors.

### Exact reconstruction and duplication

Every refined fragment has a segment ledger. Each segment records absolute
source character offsets, rendered-text offsets, and either `source` or `context`.
Primary source segments partition the original exactly once. Context segments
explicitly duplicate source text, with no paraphrasing. Any inserted formatting
between segments consists only of newlines. Offsets are Python character offsets,
not UTF-8 byte offsets or tokenizer offsets.

For refined chunks, inherited `source_start`/`source_end` describe the primary
payload, while `segments` describes the complete rendered text, including copied
headings and noncontiguous context. Consumers must not assume that refined `text`
is a single source slice. Canonical chunks retain their original single-span
contract.

`reconstruct(original, children)` rebuilds from rendered primary spans, excluding
duplicated context, and checks exact equality with the canonical text. It rejects
missing/duplicated pieces, gaps, overlaps, altered text, and invalid offsets.
Reconstruction covers the canonical policy body; document-header metadata remains
preserved in fields under the unchanged loader/chunker contract.

### Structural splitting and semantic context

- Prefer complete paragraphs. Split an oversized prose paragraph at conservative
  English sentence boundaries; avoid recognized abbreviations, titles, and initials.
  An oversized indivisible sentence is reported, never sliced by token position.
- Keep list items and their wrapped/nested content together. Repeat a preceding
  governing paragraph when splitting a list. Oversized items with their context
  are reported rather than separated from their conditions.
- Pack complete table rows, repeating the original header and separator and
  preceding governing paragraph. Repeat the immediately following qualification
  when it fits with every row. A whole table remains together when it fits with
  the required local context. Oversized rows are reported instead of cutting cells.
- Preserve fenced blocks atomically. Unsupported or unsafe blocks produce a
  `RefinementIssue` associated with the original chunk and citation. A failed
  original emits no partial fragments. `require_complete()` and the CLI refuse
  encoding if any original has an issue.

**Exact reconstruction is not semantic completeness.** All 63 newly created
fragments carry `required_context_ids` for their siblings from the same original.
This records that the complete original section remains the evidence context.
It avoids pretending that a parser can infer every distant qualification or
exception. The CLI explicitly reports these dependencies. A future retrieval
consumer must fetch the required context and preserve cross-policy references
before presenting an answer; this task does not implement that consumer.

For the reviewed PLAT-001 §6.1 context requirement, the regeneration paragraph
and the complete Change Management conditions paragraph are an indivisible bundle.
The authorized-reviewer paragraph is repeated alongside them. All three complete
paragraphs physically fit in one **249-token** encoding input, rather than merely
being connected by an ID. A separate semantic regression test verifies their exact
co-presence. The bundle is pinned to the reviewed PLAT source hash; a changed
source requires review of this explicit recipe. A test with a 240-token budget
verifies that the bundle is rejected rather than weakened.

This is a deliberately bounded Markdown parser, not general natural-language
understanding. Sentence heuristics, unfamiliar Markdown, and future policy
revisions need inspection. No independent-fragment answer-quality claim is made.
Some context still spans fragments and other policy sections; the required sibling
links make the former explicit, while existing source citations preserve the latter.

### Alternatives and tradeoffs

Fixed token windows would be simpler but could separate conditions, list items,
and table cells. Replacing the canonical chunker would couple source organization
to one model. A longer-input model could reduce fragmentation but would change
the embedding space and runtime requirements. This refinement adds 38 embedding
inputs and some duplicated context while retaining the approved model and the
original source representation. No new dependencies or model downloads are needed.

## Vector Representation and Storage Compatibility

An embedding is a fixed-length numerical representation learned so that useful
semantic relationships can be compared mathematically. An embedding encoder
returns vectors; a generative LLM produces text tokens. Neither operation alone
proves a policy answer is grounded or that a draft is authoritative.

The dimension is the number of coordinates, not a quality score. A 384-dimensional
model requires stored and query vectors with that same length. Matching lengths
are necessary but insufficient: different models can produce incompatible spaces
with identical dimensions.

Document and query embeddings are commonly compared using cosine similarity:
`dot(document, query) / (norm(document) * norm(query))`. For unit-length vectors,
the dot product equals cosine similarity. This task does not implement search.

Chroma or Pinecone can later store these vectors keyed by chunk ID alongside
source metadata. Moving between databases can reuse vectors when the model,
revision, pooling/prompts, normalization, and input preprocessing remain consistent
and the destination is configured for the same dimension and distance metric.
Changing the embedding model generally requires re-embedding the corpus and
switching query encoding to the same model. Equal dimensions do not make model
outputs interchangeable. No Chroma or Pinecone integration is implemented here.
