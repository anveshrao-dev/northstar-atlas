# Local Chroma Vector Storage

> Historical engineering record. Proposals, scope limits and dated measurements
> describe the work at that time, not current setup or operational authorization.
> See the [current architecture and experiment guide](../README.md) and
> [project README](../../README.md) for the implemented system and remaining limits.

## Purpose and boundary

Chroma persists the verified policy chunks and their MiniLM vectors, then returns
nearby chunks for a query vector. This component implements local indexing and
similarity search, with citations and required sibling context. It does not
generate answers or establish retrieval quality. No Pinecone, BM25, hybrid search,
reranking, LLM, or LangGraph integration is included.

Chroma was chosen for a small experiment that can reopen a local database without
a server, account, credentials, or paid API. A direct NumPy comparison would be
simpler for 189 vectors, but would not exercise persistent collection management.
Pinecone would introduce a managed remote service and deployment decisions; the
embedding model, dimension, metric, IDs, and metadata contracts still matter when
moving between databases. [Chroma persistent client documentation](https://docs.trychroma.com/docs/run-chroma/clients).

## Collection and metadata

The project-owned collection is `northstar_atlas_policies_v1`, persisted only in
`.local/chroma/`. Chroma receives `embedding_function=None` on both creation and
opening, explicit vectors, and HNSW `space="cosine"`. Telemetry is disabled,
OpenTelemetry has no endpoint, and Chroma's `.env` loading is disabled. Chroma
1.5.9 represents the disabled embedding function as `{"type":"legacy"}` internally;
the adapter checks that raw configuration without constructing an embedding model.

The collection configuration pins:

- MiniLM model ID and revision `1110a243fdf4706b3f48f1d95db1a4f5529b4d41`;
- 384 dimensions, L2 normalization, and a 256-token budget;
- canonical chunking `section-v1`, refinement `token-context-v1`, and metadata schema 1.

Each Chroma ID is the existing canonical/refined chunk ID. Scalar metadata contains
document ID, title, version, department, status, effective date, section, path,
source hash, citation, model provenance, and original chunk ID. An integer date
ordinal permits effective-date filtering. Deterministic JSON strings retain all
remaining dataclass metadata, source/context spans, and required sibling IDs.
Round-trip checks ensure the JSON and filter columns agree. Chunk text is stored
as Chroma's document field, including explicitly tracked duplicated context.

`records.py` handles metadata and context validation; `store.py` handles Chroma,
locking, index state, and search; `pipeline.py` connects the unchanged verified
loader, canonical chunker, refiner, and embedding interface. The CLI is in
`vector_store/__main__.py`. No existing ingestion component changed.

## Indexing, updates, and recovery

`index_corpus()` validates the manifest and every source hash, loads all six
policies in draft-review mode, makes canonical chunks, refines oversized inputs,
verifies lossless source reconstruction, checks token counts, and embeds the full
batch. It rechecks the corpus fingerprint after encoding, before storage. Unsafe
refinement or invalid vectors abort without publishing partial records.

`synchronize()` checks unique IDs, vector shape/finite values/normalization, model
configuration, and complete sibling families. It then takes a project-local
advisory file lock and atomically publishes an **incomplete** sidecar before any
record mutations. It upserts bounded batches, removes IDs absent from the verified
new corpus, and compares persisted records and float32 vector directions with the
inputs (coordinate tolerance: relative 1e-5, absolute 1e-6 after normalization).
Only then does it publish **ready**, including corpus, record, and vector digests.
The vector digest fingerprints the actual persisted bytes after that comparison.
Source hashes are compared per document and changes are reported.

Reindexing always regenerates/upserts vectors. “Unchanged” means unchanged ID,
text, and metadata, not skipped inference. This favors a simple recovery path
over incremental embedding caches at the current corpus size. Obsolete cleanup
is limited to this project's named collection. Indexing never filters out drafts;
retrieval eligibility is a separate decision.

Queries refuse absent, incomplete, stale, incompatible, or integrity-failing
indexes. A failed preflight leaves an existing valid index intact; a failure after
mutation starts leaves the incomplete marker. The local lock prevents overlapping
operations through this adapter. Chroma operations and the sidecar do not form a
multi-operation database transaction, and direct external writers must not run
concurrently.

Recovery procedure:

1. Stop the competing local operation if `status` reports busy; retry afterward.
2. Inspect `status` and the reported error. Correct source/manifest or cached-model
   problems through the appropriate approved workflow; do not bypass validation.
3. Rerun `index`. With the same compatible configuration, it overwrites current
   records, removes obsolete/malformed records, verifies vectors, and publishes ready.
4. Run `status` again, then search. Never manually change `index-state.json` to ready.

Database-level corruption, an incompatible model/schema, or a changed PLAT-001
semantic-context recipe requires investigation and a separately reviewed rebuild
decision. There is no automatic database deletion, dependency upgrade, or migration.

## Retrieval and context

`search_corpus()` verifies the current manifest and source hashes before querying.
`approved_only` is the default: status must be `Approved (Synthetic)` and its
effective date must be no later than the reference date (UTC today by default).
As of 2026-10-22, this permits only the 19 HR chunks. `draft_review` explicitly
includes all six policies, retaining their proposed labels; it is not permission
to treat drafts or future-effective documents as current approved authority.

`search()` embeds the query using the same model configuration and applies the
metadata filter inside Chroma. It returns ranked `SearchHit` values with chunk,
model, cosine distance, cosine similarity, and unranked required sibling chunks.
All required siblings must exist and share document, version, source hash/path,
section, status, effective date, original identity, and refinement configuration.
Missing or ineligible context fails the request instead of silently weakening it.

Cosine distance is `1 - cosine similarity`; smaller distance means closer vectors.
Neither score is answer confidence or a correctness probability. HNSW is an
approximate nearest-neighbor index. A nearest result is always relative to the
eligible corpus, even if the question is unsupported. No relevance threshold,
answerability decision, or answer generation is implemented.
[Chroma distance configuration](https://docs.trychroma.com/docs/collections/configure).

Required siblings expand each ranked hit beyond top-k and can repeat across hits.
They receive no fabricated similarity score. This preserves the M2.3 context
contract but is not a general cross-policy dependency resolver. A future consumer
must deduplicate context and preserve qualifications when assembling evidence.

## Commands

Run from the project root using the existing environment. No model download is
performed by these commands. Full policy text is omitted unless `--show-text` is
explicitly supplied to search.

```bash
export TMPDIR="$PWD/.local/tmp"
export PYTHONDONTWRITEBYTECODE=1
export HF_HUB_OFFLINE=1
export TRANSFORMERS_OFFLINE=1
.venv/bin/python -B -m northstar_atlas.vector_store index
.venv/bin/python -B -m northstar_atlas.vector_store status
.venv/bin/python -B -m northstar_atlas.vector_store search "When must a departing employee's access be disabled?"
.venv/bin/python -B -m northstar_atlas.vector_store search "Who approves a Terraform production plan?" --mode draft_review --top-k 3
NORTHSTAR_RUN_MODEL_TESTS=1 .venv/bin/python -B -m unittest discover -s tests -v
.venv/bin/python -B scripts/validate_evaluations.py
```

`status` does not load MiniLM. It returns a nonzero exit code for an absent,
incomplete, stale, or incompatible index. Tests create real Chroma databases only
under `.local/tmp`, with deterministic fake vectors; an opt-in integration test
uses the cached MiniLM model and both PLAT-001 §6.1 fragments.

## Observed results

Initial indexing stored **189 unique records** from 151 canonical chunks; the
longest embedding input was **254/256 tokens**. The first run spent 12.128 seconds
loading MiniLM, 10.756 seconds encoding, and 14.248 seconds in the indexing workflow
excluding model load. Reindexing reported 0 inserted, 0 updated, 189 unchanged,
0 deleted, and 189 total. A separate process reopened the persistent collection.

| Policy | Records |
| --- | ---: |
| HR-001 | 19 |
| IT-001 | 25 |
| PLAT-001 | 46 |
| SRE-001 | 35 |
| SEC-001 | 34 |
| COMP-001 | 30 |

All persisted vectors have 384 finite coordinates; measured norms ranged from
0.9999999193 to 1.0000001113. All 40 required evaluation evidence references remain
addressable in stored metadata. The existing canonical warning for the 4,179
character PLAT-001 §2 table remains visible; refinement resolves its model budget
without dropping content.

| Query/mode | First result | Distance | Similarity |
| --- | --- | ---: | ---: |
| Departing employee access / approved_only | HR-001 v1.0 §5.2 (approved, synthetic) | 0.339437 | 0.660563 |
| Terraform production plan / draft_review | PLAT-001 v0.1 §6.1 (proposed) | 0.303187 | 0.696813 |

The Terraform hit includes its required sibling, retaining the technical approval
and Change Management scope conditions. The next draft-review hits were PLAT-001
§4.2 and §4.1. Query timings in one warm-model run were 5.191 seconds for the first
query (including initial Chroma opening/imports) and 0.096 seconds for the next.
These are local observations, not performance guarantees.

The final complete run passed **130 unittest tests in 47.352 seconds, with zero
skips or failures**, including the cached MiniLM integration. The standalone M1.8
validator passed all 15 questions and source/manifest/evidence checks. New tests
cover update/removal, repeat indexing, full-sized batches, metadata round trips,
date/status filtering, mismatched configurations/vectors, interrupted writes,
malformed-record recovery, vector-only corruption, missing/cross-source siblings,
local locking, symlink rejection, and a separate-process reopen/query.

Two implementation issues were found and corrected during validation: malformed
old metadata initially prevented recovery; and exact input-to-storage vector-byte
comparison rejected legitimate differences of at most 1.49e-8 in a full-corpus
run. The latter left the index incomplete as designed. Numerical direction
verification followed by a persisted-byte digest resolves that issue while still
detecting later altered vectors. The successful recovery run reported 189 unchanged
records, 9.852 seconds encoding, 12.949 seconds indexing excluding the 11.280-second
model load, followed by a successful fresh-process status and query. A validation
script also initially attempted a query while holding the adapter lock; releasing
the inspection lock before querying resolved that harness error.

The persisted directory occupied **7,996,167 logical bytes (7.626 MiB)** after the
validation runs; repeated writes and database housekeeping can change its size.
The final baseline audit found only `pyproject.toml` and `uv.lock` changed among
existing files, plus the five new vector-store modules, their test module, and
this note. All policies, manifest, evaluation files, prior code, and Git metadata
remained byte-for-byte unchanged. `.local`, `.venv`, and `.env` remain ignored.
No commits, pushes, cloud resources, or paid API calls occurred.

## Limits and next evaluation

Integrity checks read the whole small collection on each query; this is deliberate
for 189 records and will need a different strategy at scale. Sidecar digests detect
accidental changes, not a malicious actor able to replace both data and digests.
The local database has no application authentication layer. Source files should
remain stable during indexing; the checks are not filesystem snapshot isolation.

Successful indexing, evidence addressability, and two plausible search examples
do not prove retrieval recall, unsupported-question handling, or answer accuracy.
A future approved evaluation should measure relevant evidence in top-k, required
context completeness, mode isolation, and unsupported questions before tuning.
No evaluation-based tuning was performed in this experiment.
