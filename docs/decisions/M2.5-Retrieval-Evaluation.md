# Chroma Retrieval Evaluation

> Historical engineering record. Proposals, scope limits and dated measurements
> describe the work at that time, not current setup or operational authorization.
> See the [current architecture and experiment guide](../README.md) and
> [project README](../../README.md) for the implemented system and remaining limits.

Evaluated: 2026-10-22. Scope: local dense retrieval against the fixed M1.8
development dataset. No index rebuild, retrieval tuning, dependency changes,
policy edits, or answer generation were performed.

The reproducible **complete-source-section coverage proxy** gives macro
Recall@5 of **55.22% directly** and **64.67% with required siblings**. Full
coverage rises from **4/15 to 6/15 questions**. These are conservative structural
coverage measurements, **not human-adjudicated semantic Recall under the M1.8
rubric**. The distinction matters: some useful excerpts contain the necessary
facts without containing every line of their source section.

## 1. Evaluation Setup

- Dataset: 15 questions, 40 document-qualified required evidence references.
  Categories: A (3 precise HR lookups), B (6 multi-document questions), C (3
  ambiguous questions), D (3 unsupported requests for approved values/procedures).
- A uses `approved_only`; B/C/D use `draft_review`, exactly as specified in the
  dataset. The explicit authority reference date is `2026-10-22`.
- Existing collection: `northstar_atlas_policies_v1`, under `.local/chroma/`.
  All 189 records were ready and compatible. Canonical chunking, token refinement,
  stored document vectors, metadata filtering, and sibling expansion are unchanged.
- Each question is queried once, in dataset order, for five ranked chunks.
  Only question text and retrieval mode enter the retriever. Expected answers,
  evidence labels, review reports, and evaluation files are not retrieval sources.
- The cached MiniLM model encodes queries locally. No downloads, installations,
  cloud calls, generation, lexical search, fusion, or reranking occur.

Implementation: `evaluation/retrieval.py` separates pure `score_question` and
`summarize` functions from `evaluate`, which validates the dataset/index, executes
queries, checks preservation, and records provenance. `EvidenceCatalog` verifies
returned chunks against the existing canonical/refined representations and checks
source-span coverage. `write_results` exclusively creates a new project-local JSON
file; it rejects existing destinations and paths resolving outside the project.

Reproduce from the explicitly authorized checkout after verifying its resolved path:

```bash
pwd -P
export TMPDIR="$PWD/.local/tmp"
export PYTHONDONTWRITEBYTECODE=1
export HF_HUB_OFFLINE=1
export TRANSFORMERS_OFFLINE=1
.venv/bin/python -B -m northstar_atlas.evaluation.retrieval --reference-date 2026-10-22
.venv/bin/python -B scripts/validate_evaluations.py
NORTHSTAR_RUN_MODEL_TESTS=1 .venv/bin/python -B -m unittest discover -s tests -v
```

The evaluation CLI chooses a new timestamped artifact by default; `--run-name`
sets a new filename stem. A stale, incomplete, incompatible, or changing index
fails evaluation rather than triggering a rebuild. Resolve such a failure through
a separately authorized indexing action before rerunning.

## 3. Metrics and Scoring Definitions

The M1.8 rubric requires semantic support for facts, actors, conditions, and
exceptions, with human adjudication. This implementation supplies a deterministic
conservative proxy and targeted qualitative inspection; it does not silently
replace that rubric with section-ID overlap or claim semantic adjudication is done.

An evidence unit is `(document_id, section_id)` from `required_evidence`. A unit
gets proxy credit when eligible, provenance-verified retrieved source spans cover
the entire canonical source section. Duplicated context can contribute because
that text was actually returned. An unretrieved source is never added to context
to rescue a miss. Merely mentioning another policy or returning a heading is
insufficient.

For a parent reference, **all of its own content and all dot-delimited descendant
sections in the same document** must be covered. `4` includes `4.1`, but not
`40.1`, and never matches another document. One subsection alone does not satisfy
a parent. This deliberately strict definition avoids ambiguous parent matching.

Let R be the required units and H be the units covered by the evaluated context:

| Metric | Per-question definition |
| --- | --- |
| Recall@5 | `len(H) / len(R)` |
| Hit@5 | 1 if at least one required unit is covered, otherwise 0 |
| Full Evidence Coverage@5 | 1 if all required units are covered, otherwise 0 |
| Reciprocal Rank@5 | Reciprocal of the earliest direct rank whose prefix completes a required unit; zero if none |
| MRR@5 | Mean of per-question reciprocal ranks |

All averages are macro averages over questions, not a pooled count of evidence
units. Duplicate sections consume top-five slots without repeated credit. Several
fragments may jointly complete a unit; consequently the first complete unit can
occur later than the first useful fragment.

**Direct** uses only the five ranked chunks. **Expanded** adds their explicitly
required, verified siblings and deduplicates by chunk ID. Expanded RR uses the
earliest **direct trigger-prefix** whose expanded context completes a unit; it is
reported as expansion-trigger MRR, not a rank assigned to a sibling. Sibling JSON
records have null ranks/distances and record trigger ranks and validity per
occurrence. Expanded context may greatly exceed five chunks.

`section_id_recall_at_5` is an additional ID-presence diagnostic, never semantic
credit. Here it is 64.67% in both views. Future nonempty alternative-evidence
labels are explicitly rejected until their scoring is implemented and reviewed.
Invalid status/provenance is excluded from credit and reported independently.

Cosine distance is lower for closer vectors; cosine similarity is `1 - distance`.
Neither is answer confidence, proof of authority, nor a calibrated probability.
No confidence threshold is inferred from this run.

## 4. Overall Results

| Metric, all 15 questions | Direct top 5 | Top 5 + required siblings |
| --- | ---: | ---: |
| Macro Recall@5 | 55.22% | 64.67% |
| Hit@5 | 86.67% (13/15) | 93.33% (14/15) |
| Full Evidence Coverage@5 | 26.67% (4/15) | 40.00% (6/15) |
| MRR@5 / expansion-trigger MRR | 0.6944 | 0.8667 |
| Authority leakage / validation violations | 0 / 0 | 0 / 0 |

For the nine answerable A/B questions alone, recall is **67.96% → 80.00%**,
Hit@5 is **100% → 100%**, full coverage is **3/9 → 5/9**, and MRR is
**0.8426 → 1.0000**. None of these figures measures answer correctness.

Mean retrieval latency was **0.407709 s**. The slowest was EVAL-001 at
**3.914559 s**, the first inference query; the remaining 14 averaged **0.157220 s**.
Model loading took **12.979454 s** and total model/refinement setup **13.385917 s**,
excluded from retrieval timing. Each retrieval time includes source/integrity
validation, query embedding, Chroma search, and sibling fetching. It is not a
database-only benchmark. Scoring, token accounting, and output writing are excluded.
There was no benchmark-query warmup and only one measured pass per artifact;
latency is an observation, not a service-level guarantee.

Mean context grew from **791.27 to 1,296.13 MiniLM tokens** (+63.8%). Counts sum
each chunk including its special tokens and duplicated context; they are not a
future generation model's prompt-token count. EVAL-006 expanded from 5 to 15
unique chunks and from 1,021 to 3,322 tokens. Expansion improves completeness at
a measurable context cost; it does not recover arbitrary missing sections.

## 6. Three Successful Retrieval Examples

1. **EVAL-001 — planned versus urgent transfer notification.** Rank 1 is
   `HR-001 v1.0 §4.2 (approved)` at cosine distance 0.1360. The actual section
   preserves both planned and urgent cases. All three precise HR questions have
   complete evidence at rank 1 under approved-only filtering.
2. **EVAL-005 — regenerated Terraform plan.** Top five include
   `PLAT-001 v0.1 §§6.1, 4.3 (proposed)` and
   `COMP-001 v0.1 §8.2 (proposed)`. The rank-1 §6.1 excerpt preserves renewed
   authorized technical review and the conditions for staying within Change
   Management scope/risk/window. Its first distance is 0.1772. The COMP sibling
   adds the sanitized-evidence restriction against ordinary audit packages
   containing raw secret-bearing plans/state. Proxy coverage rises 2/3 → 3/3.
3. **EVAL-013 — unavailable retention duration.** Rank-1
   `COMP-001 v0.1 §11.1 (proposed)` at distance 0.2597 supplies the explicit
   absence of a numeric approved duration. Retrieval successfully finds the
   limitation evidence while preserving draft authority.

## 7. Three Weakest Cases

1. **EVAL-015 — approved GCP deployment procedure:** 0/3 in both views. Top
   results focus on production CR requirements and execution, rather than the
   requested procedure's absence. General topic relevance does not establish
   scope or approval. Siblings restore the same sections, not the missing units.
2. **EVAL-004 — developer transfer to SRE:** 1/5 in both views. IT-001 §6.3 at
   rank 1 explains that team membership does not grant production administrator
   access, but the top five concentrate on IT role changes. HR removal/exception
   rules and Security approval/MFA evidence are missing. An answer needs more
   than the locally relevant IT handoff paragraph.
3. **EVAL-010 — failing Jenkins job:** 0/3 → 1/3 under the strict proxy. Useful
   hosting/component conditions are present directly, but required Security and
   incident-scope sections are absent. Expansion restores the whole SRE table
   without resolving the missing cross-document evidence.

## 8. Root-Cause Hypotheses and Scoring Tradeoffs

These are hypotheses from inspected results, not causal conclusions from ablations:

- Dense similarity favors the immediate topic (Jenkins, transfer, deployment).
  A single compound question may not rank all its authority, lifecycle, and
  security dependencies within five slots.
- Several fragments from one section can occupy multiple ranks. This preserves
  useful text but leaves fewer opportunities for another required document.
- Required-sibling expansion repairs fragmentation within a canonical chunk
  family. It is not a dependency-graph search across cited policies.
- Unsupported questions can retrieve convincing general procedures instead of
  explicit limits. Similarity or draft labels alone do not solve this distinction.
- Strict complete-section coverage can under-credit semantic sufficiency. For
  EVAL-005, the rank-1 §6.1 semantic bundle already contains the critical drift
  conditions, though the whole section is complete only by rank 3. For EVAL-006
  and EVAL-010, the directly returned Jenkins table row is relevant; restoring
  unrelated table rows improves the proxy without necessarily adding needed
  Jenkins facts. Do not interpret every proxy increase as an equal semantic gain.

Exact ID overlap would be simpler but could reward a fragment missing conditions.
Complete-source coverage is reproducible and conservative but can over-demand
irrelevant material. Human adjudication against expected claims/qualifiers is the
next step for true M1.8 semantic Recall. No LLM judge or automatic paraphrase-based
grader is introduced here.

## 9. Planned Comparisons

This artifact freezes queries, eligible modes, reference date, source hashes,
model revision, vectors, chunking, top-k, sibling assembly, and scoring version.
Use those same inputs for future controlled comparisons:

- **Pinecone dense:** preserve vectors, IDs, cosine interpretation, filters,
  effective-date checks, and sibling rules. Compare rankings/coverage and measure
  network-inclusive latency separately. A database migration alone does not fix
  embedding representation or missing policy dependencies.
- **BM25:** measure a lexical baseline on the same text and authority filters to
  test whether named technologies and exact governance terms recover missed units.
- **Hybrid or reranking:** only after separate authorization, declare candidate
  budgets, fusion/reranker settings, final top-k, and total context tokens. Compare
  direct and expanded evidence separately. Do not hide extra text behind the same
  nominal top-five label.

Keep this baseline immutable. Use new run names and record any later scoring,
corpus, or label version. Preserve a held-out evaluation set before tuning; these
15 development questions should not become the sole optimization target.

## 10. Validation, Limitations, and Next Steps

- **148 tests passed in 48.381 s**, with real cached-model tests enabled and no
  skips. This includes 18 new evaluation tests covering metrics, duplicates,
  parents, status/date eligibility, missing units, provenance, sibling auditing,
  invalid data, deterministic formatting, output isolation, and rejection of
  incomplete/stale or changing indexes/corpora.
- M1.8 validator passed: 15 unique questions, category counts 3/6/3/3, valid
  source hashes, manifest pin, evidence references, modes, and behaviors.
- Real evaluation completed all 15 queries twice, with identical ranked IDs,
  distances, and metric values; no authority/provenance violations occurred.
- The existing 81 project/Git files captured before work remained byte-identical.
  New files are this note, `evaluation/__init__.py`, `evaluation/retrieval.py`,
  and `tests/test_retrieval_evaluation.py`; generated runs/logs stay under `.local/`.
- The ready count (189), corpus fingerprint, record digest, and vector digest
  were unchanged before/after evaluation. No application upsert, deletion, or
  rebuild was called. **Physical database files were not byte-identical:**
  Chroma opening/querying changed `chroma.sqlite3` and `data_level0.bin` while
  verified logical contents stayed unchanged. This is consistent with library
  persistence housekeeping; its precise internal cause was not investigated.
- No packages, source policies, manifest, dataset, or existing pipeline code
  were modified; no commit, push, or cloud service was used. Test databases are
  temporary project-local fixtures, separate from the preserved corpus index.

Fifteen overlapping synthetic development questions are too small for general
quality claims or statistical significance. Exact reconstruction proves text
coverage, not understanding. This proxy is not human semantic adjudication;
targeted excerpt inspection is not exhaustive semantic scoring. No precision,
generated-answer correctness, faithfulness, citation accuracy, clarification, or
abstention success has been measured. No answer model ran.

Before answer generation, review missing cross-document evidence, adjudicate
whether partial sections retain the relevant qualifiers, define an explicit
context budget, and design grounded handling of missing/ambiguous evidence and
draft status. A high Hit@5 or MRR can coexist with poor full-evidence coverage;
finding one useful rule is different from supplying every required condition.
Metadata filtering protects authority, source spans make coverage auditable,
and frozen provenance makes later backend experiments comparable.

This evaluation measured local dense retrieval only; it did not implement managed
retrieval, BM25, hybrid search, reranking or answer generation.
