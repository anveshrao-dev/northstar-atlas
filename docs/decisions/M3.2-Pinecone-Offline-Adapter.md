## 1. Scope and Azure decision

The owner's latest instruction selects Azure and continues M3.2 after updating
[M3.1](M3.1-Pinecone-Design.md). The selected future placement is Pinecone-managed
serverless on **`azure` / `eastus2`**, with Builder. Public plan/region documentation

normalized vectors, cosine search, deterministic refined IDs, and immutable
snapshot namespaces. Chroma remains the default working backend and its CLI is
unchanged. There is deliberately no remote CLI, credential loader, provisioning
function, or automatically constructed Pinecone client in this milestone.

## 3. Components and contracts

| File | Responsibility |
| --- | --- |
| `vector_store/contracts.py` | Shared `SearchHit` and structural `RetrievalStore` protocol; distance remains `1 - similarity`, not answer confidence |
| `vector_store/preparation.py` | Existing manifest/source validation, canonical chunking, token refinement, reconstruction and encoding; `freeze_snapshot` validates/fixes float32 representation and deterministic namespace identity |
| `vector_store/pinecone_state.py` | Target-scoped `.local/pinecone/<target-digest>/` manifests, local writer lock, symlink/path checks, durable atomic publication |
| `vector_store/pinecone_store.py` | Injected Documents API adapter: target/schema checks, bounded upserts, audits, visibility probes, publication/recovery, authority filters and sibling expansion |
| `vector_store/pipeline.py`, `store.py` | Reuse preparation and compatibility-export `SearchHit`; existing Chroma behavior retained |
| `tests/test_pinecone_store.py`, `test_pinecone_state.py` | Offline failure/recovery and SDK-wire tests, plus cached MiniLM corpus integration |

`prepare_corpus(root, provider)` reuses the same six verified sources, tokenizer
and lossless refinement. `freeze_snapshot(records, config, fingerprint)` accepts
only unique IDs, complete sibling families, compatible model metadata and finite,
L2-normalized vectors. It preserves chunk metadata and sorts records only for
transport identity. Source order remains in chunk indexes and spans.

The namespace digest includes corpus fingerprint, full configuration, wire-schema
version, exact text/metadata and frozen float32 vectors. It is independent of
request time and input list order. Metadata uses the same deterministic JSON
strings as Chroma. Known integer fields may return as integral floats; fractional,
nonfinite or boolean values fail validation. Unexpected/altered fields fail exact
payload checks before the existing `decode_chunk` reconstructs the record.

`PineconeStore` requires an explicit frozen snapshot, `PineconeTarget`, Documents
handle, target-description callable and fresh corpus-fingerprint callable. These
are injected for testing; the adapter does not read `PINECONE_API_KEY` or `.env`.
Production wiring and explicit backend-selection/evaluation runners remain for
the separately approved cloud integration. A target's project ID is a declared
local identity: index description validates host/name/schema/placement, but does
not independently attest account/project ownership. That must be checked before
any real client is wired or upload approved.

The adapter also checks the injected Documents handle's `_host` against the
selected target before operations. This is an explicitly tested SDK 10.0.0 internal
attribute; a future SDK upgrade must revalidate that boundary.

## 4. Publication, retrieval and recovery

Preflight checks all payloads before transport: conservative 40,000-byte metadata
budget including text, ASCII IDs up to 512 characters, at most 50 records and
1,000,000 encoded bytes per request. Nothing is silently truncated.

The writer records an incomplete manifest, upserts deterministic batches, checks
acknowledged counts, lists every ID through SDK pagination, fetches and verifies
every payload/vector, and performs a self-vector search filtered to each record
ID. Only after visibility and a fresh source check does it write ready state and
atomically replace `active.json`. Search pins one namespace including siblings.
Pagination checks whole pages, repeated continuation tokens, a finite page budget
and deadline, including empty pages that item-level iteration would not expose.

An identical ready snapshot is audited and reused without upserts. Changed sources
or vectors produce a new namespace; the previous generation remains inactive.
At most three retained owned generations are allowed until explicit cleanup.
Cleanup requires an exact approved inactive namespace and injected deletion
transport; it never uses an unscoped record deletion. Only fake cleanup was tested.

Recovery is explicit:

1. Fix the underlying transport/visibility issue; retain manifests and source data.
2. Reconstruct or retain the **same frozen snapshot**, configuration and target.
3. Call `synchronize()` again after cloud-operation authorization. It verifies
   existing records and can resend identical batches after unknown write outcomes.
4. Tampered records, unknown ownership or extra IDs block automatic repair. Inspect
   and approve a scoped recovery separately; do not clear a namespace blindly.
5. A crash between ready-state and pointer publication can safely resume publication.
   Missing local state is not automatically adopted. Current source hashes must
   match; there is no silent fallback to an older corpus or to Chroma.

The first query after reopening performs a full remote integrity audit. Later
queries validate their returned records and siblings; explicit `audit()` supports
evaluation boundaries. Failed audits and search integrity checks invalidate
readiness and the cached audit; subsequent queries remain blocked until
reconciliation. A transport failure alone is not treated as proof of corrupt data.
`status()` reports
local state only and explicitly does not claim a current remote audit.

Approved-only is the default, filtered before ranking by exact approved status and
effective date. Draft-review preserves draft labels. Required siblings are fetched
from the same namespace and matched against the frozen source/model identity;
missing or ineligible siblings fail the request. Siblings receive no ranking score.

Calls use 10-second per-attempt timeouts and no application retry loop. Visibility
polling is bounded by 60 rounds and a 300-second polling deadline; an in-flight
SDK operation can exceed that deadline because of its own finite retries. Errors
are sanitized, with the failed operation retained. LSN-based freshness is not
assumed: this adapter uses the conservative per-ID visibility fallback. Live
retry/usage/LSN behavior still needs a separately authorized integration test.

## 5. Validation

The focused suite passed **26 tests**, including all 189 actual cached-MiniLM
records, in 50.437 seconds. The integration used the installed SDK's real Documents
serializer, response decoder and paginator with an in-memory HTTP boundary;
socket connections were blocked. Both retrieval modes and a real query embedding
were exercised. Reindexing reused the same namespace with no duplicate upserts.
The fake boundary's scores/ranks are fixtures, not retrieval-quality measurements.

After the independent review and regression fixes, the complete suite passed
**176 tests, no skips, in 61.974 seconds**: 148 existing tests plus 27 new unit
tests and one new cached-model offline integration test. The reviewer identified
three issues, each reproduced before correction: mismatched injected transport
host, readiness remaining cached after a search integrity failure, and unbounded
empty-page pagination. All three regression checks now pass.

`uv sync --locked --extra pinecone --offline --dry-run` would make no changes;
`uv pip check` confirms all 107 installed distributions are compatible. All 102
pre-existing installed distribution versions are unchanged. Hash comparison with
the task baseline confirms the six policies, corpus manifest, evaluation files
and all seven production Chroma files are unchanged. The only changed pre-existing
project files are M3.1, pyproject.toml, uv.lock, pipeline.py and store.py; new files
are listed above. Markdown/whitespace checks passed. No compatibility warning was
emitted by the final suite. Validation logs stay in `.local/m32-tests-final.log`.

M1.8 validation passed all 15 questions, category counts, source hashes, evidence
references, modes and expected behaviors. No evaluation data or scoring rules were
changed. The production Chroma database was not opened for this work.

Reproduce validation from the project root after installing the approved extra:


## 6. Boundaries and remaining approvals

Offline tests cannot establish account entitlement, regional capacity, real service
consistency, latency, quotas, cost or retrieval quality. No Pinecone index, namespace
or key was created or used. No real remote request was made. The local publication
lock supports one project writer; it is not a distributed lock or remote integrity
service. Frozen snapshots are in-memory values; manifests hold their identity and
expected IDs, not a new durable vector export. Future comparison must export and
verify the original Chroma float32 matrix before claiming identical-vector parity.

Before provisioning: reverify Builder and `azure/eastus2` availability; verify the
account/project/index host, budget and key scope; obtain approval to provision and
upload synthetic records. If `eastus2` is unavailable, present supported Azure
alternatives and wait for selection. Azure selection is not provisioning approval.
Linux/Replit still needs its own native-wheel/runtime check and model cache setup.

The embedding model defines the vector space; the database stores/searches
it. Stable IDs prevent duplicate records, while immutable generations prevent mixed
corpus versions. Publication state distinguishes acknowledged writes from verified
searchable data. An offline SDK test proves our API contract, not cloud behavior.
These checks cover the offline adapter, not live retrieval evaluation or answer generation.
