# BM25 and Hybrid Retrieval Design

**Status:** Proposed; implementation requires approval.  
**Date:** 2026-10-24.  
**Scope:** Local keyword retrieval, rank fusion, and a controlled retrieval comparison. No implementation, dependency installation, provider calls, index rebuilds, or answer-generation experiment is authorized by this document.

This historical design preceded implementation. See [implementation and results](M5.2-Hybrid-Retrieval-Results.md)
and the [final evaluation](M7.1-Final-Evaluation.md) for the implemented state.

## 1. Recommendation and alternatives

Add a small standard-library BM25 scorer over the existing **189 refined chunks**, then combine its ranked results with Chroma using equal-weight Reciprocal Rank Fusion (RRF). Keep dense retrieval as the application default until the comparison is reviewed. Separate retrieval strategy (`dense`, `bm25`, `hybrid`) from dense backend (`chroma`, optionally `pinecone`).

| Approach | Benefit | Tradeoff / decision |
| --- | --- | --- |
| Standard-library BM25 | No dependency change; transparent formula and deterministic behavior; bounded work for 189 records | We own scoring, tokenization and correctness tests. Recommended for this experiment. |
| `rank_bm25` | Existing BM25 implementations; NumPy is already in the full development environment | Adds an approved/pinned dependency and still needs our metadata, eligibility and sibling adapters. Its Okapi implementation uses an IDF floor and different default `k1`; scores would not be interchangeable with the proposed variant. |
| Search service or database-native sparse search | Useful when corpus size and operational requirements grow | Adds storage/service coupling and potentially cloud changes; unnecessary for this local comparison. Deferred. |

The package comparison is based on the project's [implementation](https://github.com/dorianbrown/rank_bm25/blob/master/rank_bm25.py) and [dependency declaration](https://github.com/dorianbrown/rank_bm25/blob/master/requirements.txt). No package was installed. Parameters below are proposed starting values, not values selected by tuning the evaluation questions.

## 2. Existing system and reusable boundaries

The [loader](../../src/northstar_atlas/ingestion/document_loader.py) verifies the manifest and all source hashes. The canonical [chunker](../../src/northstar_atlas/ingestion/chunker.py) produces 151 chunks; the [refiner](../../src/northstar_atlas/ingestion/refiner.py) produces 189 embedding-ready chunks with exact source spans, explicitly duplicated context and required sibling IDs. These representations remain unchanged.

The [Chroma store](../../src/northstar_atlas/vector_store/store.py) and [Pinecone store](../../src/northstar_atlas/vector_store/pinecone_store.py) enforce readiness, source/configuration identity and eligibility, and already attach required sibling chunks. [QAService](../../src/northstar_atlas/qa.py) passes retrieval results through [context assembly](../../src/northstar_atlas/context.py), generation and grounding validation. The context builder reconstructs source families, checks identity and eligibility, deduplicates spans and includes or excludes complete evidence groups under its budget.

**Compatibility issue:** [SearchHit](../../src/northstar_atlas/vector_store/contracts.py) requires `cosine_distance`, and the context builder and [evaluation serializer](../../src/northstar_atlas/evaluation/retrieval.py) currently inspect that dense-specific field. BM25 and RRF scores must not be put in it or represented by an invented distance.

Propose one neutral ranked-evidence model alongside the existing `SearchHit`: unchanged chunk, refinement/model provenance, sibling context, and a typed score (`cosine_distance`, `bm25`, or `rrf`). Hybrid diagnostics also retain each channel's rank and raw score. Dense results convert losslessly at the boundary; their existing public contract and score interpretation remain supported. Context assembly consumes rank and verified evidence, not a guessed conversion between score types. Its source, span, citation, status and complete-family checks remain intact.

The small future change surface is the shared result normalization, BM25/fusion adapters, context input type/score checks, evaluation serialization and explicit QA factory selection. Do not replace dense adapters or generation/grounding contracts. Retain the existing search call shape for adapters; BM25 accepts but does not call the embedding provider. A BM25-only factory may supply no embedder, while dense/hybrid must require one explicitly. Keep that branch explicit; no dummy model or silent fallback. The lexical engine itself only accepts verified chunks and needs no tokenizer/model initialization.

## 4. BM25 scoring and eligibility

Index the exact `chunk.text` representation already used for embeddings, including existing heading/context duplication. Tokenization produces a separate search representation; display/citation text is never normalized or rewritten.

Proposed tokenizer `unicode-word-v1`: Unicode NFKC then case-folding, extracting runs of Unicode letters/digits (underscores and punctuation delimit terms). Thus `AKS` becomes `aks`, `IT-001` becomes `it`, `001`, `CI/CD` becomes `ci`, `cd`, and `k8s` remains `k8s`. Apply the identical rule to query and chunks. Keep stopwords, including negation; no stemming, synonyms, query expansion, phrase bonuses, metadata boosts or evaluation-specific terms. Sum over sorted unique query terms so repeated query words do not change weights or summation order.

For eligible chunks, let `N` be the count, `df(t)` the number containing term `t`, `tf(t,d)` its frequency in chunk `d`, `L(d)` its token length and `avgL` the mean length:

```text
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
BM25(q,d) = sum over unique query terms t:
  idf(t) * tf(t,d) * (k1 + 1)
  / (tf(t,d) + k1 * (1 - b + b * L(d) / avgL))
k1 = 1.2; b = 0.75
```

This uses the positive IDF convention and starting parameters documented by [Apache Lucene](https://lucene.apache.org/core/9_12_1/core/org/apache/lucene/search/similarities/BM25Similarity.html). It is a specified BM25 variant, not a promise of Lucene score parity: analyzers, length encoding and other implementation details differ. `k1` controls term-frequency saturation; `b` controls length normalization.

Compute statistics **after eligibility filtering**. For `approved_only`, require the exact supported approved status and a non-null effective date on/before the explicit reference date. For `draft_review`, allow the existing supported approved/draft states while retaining proposed labels and effective-date metadata; future-approved content must not be described as effective. Use the same predicate and date in every channel. Draft text must not influence approved-only BM25 statistics. Current approved-only eligibility yields the 19 HR chunks.

Reject invalid/blank queries and nonfinite or invalid parameters. A nonblank query with no lexical tokens or no overlap yields a diagnosed empty lexical result; it is not an authorization or system error. Zero eligible documents yield no results; an all-zero-length eligible catalog is an integrity error. Return only positive-scoring matches, at most the requested count, with stable ordering `(-score, chunk_id)`. Fixed tokenization, sorted term summation and tie-breaking make ranking repeatable for the same inputs; do not promise cross-runtime floating-point bit identity.

Common boilerplate, duplicated context and related chunks can dominate keyword scores. Preserve the 189 comparison units initially and measure that effect rather than silently removing words or collapsing families. BM25 does not understand that a matching sentence is conditional, proposed or negated; those safeguards remain downstream.

## 5. Hybrid retrieval and sibling context

Use the original question, the same eligible corpus and reference date for both channels. Retrieve up to **20 direct candidates per channel**, then produce **five direct fused hits**. The initial RRF constant is **60**, equal channel weights, one-based ranks:

```text
RRF(chunk) = sum over channels where chunk appears: 1 / (60 + rank)
```

Rank fusion combines positions rather than incomparable BM25/cosine magnitudes. The original [RRF paper](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf) describes this formulation and constant; improvement on Northstar Atlas remains an empirical question. BM25/RRF scores are ranking signals, never probabilities, cosine similarities or answer confidence.

Validate channel outputs first. Duplicate IDs within a channel, mismatched source payloads for the same ID, stale snapshots, ineligible hits or missing required context are errors. Across channels, merge equal verified IDs into one candidate, retaining both contributions. Sort fused results by `(-rrf_score, chunk_id)`. Do not round scores before ranking. Missing channel membership contributes zero. A successful empty lexical result is allowed and recorded; a failed channel aborts hybrid retrieval rather than silently switching strategy.

Only **direct candidates vote**. A sibling is not an extra ranked hit or a second RRF vote unless it independently appears as a direct candidate in a channel. Keep direct ranking separate from the deduplicated context closure. Expand all required sibling IDs for the final five, verify eligibility and the same source/refinement identity, and pass complete families to the existing context builder. If a sibling is unavailable, reject the incomplete group/result; do not publish an answer with the condition omitted.

Existing dense adapters already fetch siblings for candidate hits. Initially reuse those checks, even though requesting 20 can fetch context for candidates later discarded. Only selected hits and their required closure enter final context; unused sibling payloads do not become rescue evidence. Record this overhead. Defer changing backend fetch behavior until measurements justify it. BM25 resolves sibling IDs from the same verified local catalog.

Final context ordering follows direct fused rank; source-span deduplication and complete-group budget exclusion remain in the context builder. Exclusions and missing evidence stay visible. Related-policy references do not authorize automatic cross-document expansion. Siblings cannot recover a missing HR/Security section in a different family. Multiple direct hits from one family can consume several of the five slots, as in the frozen baseline; family diversification is a separate later experiment.

## 6. Q&A and deployment boundaries

Proposed flow: question/mode/date → chosen retrieval strategy → verified ranked evidence plus required siblings → existing context package → existing grounded-answer validation and rendering.

QAService remains reusable, Chroma remains the default dense backend, and ordinary questions remain `coverage.status = not_assessed`. Lexical matches do not create reviewed obligations or prove semantic completeness. Caller-reviewed obligations, application-owned extractive statements, citation membership, quotations, approved/draft labels and safe failure/nonpublication behavior remain unchanged. Context failure must not become a policy abstention.

The first implementation/evaluation is offline and Chroma-only. Pinecone support uses its existing adapter and target/immutable-namespace checks when separately authorized; it requires no sparse index, vector upload or cloud resource change. No silent backend switching. The Replit authored offline demonstration remains unchanged, with backend imports/provider calls disabled. A standard-library scorer does not make the complete live Q&A stack UI-only or remove its model/dependency requirements.

Use the unchanged [15-question dataset](../../evaluations/questions.json) and [scoring contract](../../evaluations/README.md). | Arm | Direct candidate selection | Final ranked evidence |
| --- | --- | --- |
| Dense baseline | Existing Chroma, `top_k=5` | Five or fewer direct hits |
| BM25 | Same verified eligible chunks | Five or fewer positive-score hits |
| Hybrid | Chroma 20 + BM25 20, RRF 60 | Five or fewer fused hits |

Also record the top five of the dense-20 candidate list as a control. Approximate indexes need not return an identical prefix when candidate count changes; distinguish that effect from lexical fusion. Generate each query embedding once and reuse it for dense/hybrid via the existing shared-query evaluation pattern. BM25 neither generates nor consumes query vectors. Do not regenerate document embeddings or reindex either store.

Reuse `complete-source-section-v1` scoring unchanged: document-qualified references require complete canonical source-span coverage; a parent reference includes its own text and all dot-delimited descendants. A subsection alone is not enough for its parent. Duplicate sections add no evidence credit. Source reconstruction, metric coverage and semantic sufficiency are distinct.

Report direct and sibling-expanded views separately:

- **Recall@5:** fraction of required evidence references completely covered.
- **Hit@5:** any required evidence covered.
- **Full Evidence Coverage@5:** all required references covered.
- **MRR@5:** mean reciprocal rank of the first direct prefix covering required evidence; in the expanded view its required sibling closure contributes coverage, never an independent sibling rank.
- Per-question missing references and macro averages by category and overall. Also report the nine answerable questions separately. Ambiguous/unsupported categories measure conditional/limitation evidence, not successful clarification or abstention by the retriever.

Measure direct/expanded unique chunk counts, characters, deduplicated source spans and context-package token bound; report complete groups excluded by the budget and coverage actually delivered after budgeting as an additional view. Do not replace the frozen pre-budget metrics with it. Use identical context preparation settings: existing Qwen bound, 32,768 context tokens, 1,024 output reservation and 512 margin, including system/question/schema overhead through offline preparation. No LLM call is required. This is a conservative bound, not billed token usage or MiniLM's 256-token constraint.

Measure initialization/catalog verification and BM25 build separately from query embedding, backend retrieval including its integrity/sibling work, lexical scoring, fusion and context assembly. Use one correctness pass and three local warm timing passes with fixed question order and rotated arm order. Report first-query observations, mean/median/max and raw timings; no tail-latency or production-throughput claims from this small run. Cache query vectors across arms, while recording their one-time generation cost. Do not repeatedly reload MiniLM for each arm.

Write new, non-overwriting artifacts under `.local/evaluations/m5/`: dataset/corpus/config hashes, algorithm/tokenizer versions, parameters, reference date, environment, per-channel IDs/ranks/raw score types, fused ranks, siblings, missing evidence, context/budget diagnostics and timing boundaries. Deterministic serialization excludes timestamps/latency from equality assertions. Never overwrite M2.5/M3.4 results or log credentials. Required evidence and expected answers belong only to scoring, never query expansion or candidate selection.

## 9. Bounded reranking experiment, deferred

Fusion combines ranks from independent retrievers. A cross-encoder reranker jointly scores the question and each retrieved text, then reorders a bounded candidate set; it cannot recover evidence absent from that set. This distinction is documented in [Sentence Transformers' retrieve-and-rerank guidance](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html).

After the dense/BM25/hybrid comparison, propose one local CPU cross-encoder, at most **20 fused direct candidates per query**, returning five. Model/revision/license, Python/Intel/Linux compatibility, download size and memory requirements need a separate selection/preflight and approval; no model is selected or downloaded here. Do not add a hosted reranker or expand the entire corpus into the experiment.

Score the question plus each exact refined candidate text. Verify the selected reranker's actual tokenizer limit including special tokens; if an input exceeds it, stop/report the case rather than silently truncate or force a misleading split. Required siblings still travel with the final hits through the unchanged context validator. The reranker sees the candidate text, not necessarily its entire sibling group, so its relevance score is not a judgment that policy conditions are complete. Record this limitation; group-aware reranking would be another experiment.

Run only if candidate-20 diagnostics show missing final-five evidence already available in the candidate pool. A proposed adoption gate is a net gain in full expanded coverage on at least one frozen question, no approved-only safety regression, and corroborating supplementary improvements with acceptable measured CPU latency/memory. One question is weak evidence, so report all regressions and human relevance review. Agree a latency budget before the model experiment; do not invent a speed guarantee. If missing evidence never enters the candidate pool, improve candidate retrieval before paying reranking latency.

## 10. Tests, implementation boundaries and risks

Following approval, keep work to a BM25 engine, neutral result normalization, fusion adapter, local evaluation extension and focused tests. Exact module layout is an implementation choice; do not add a retrieval framework, service, database, UI change or dependency for these functions.

Required offline tests:

1. Hand-calculated BM25 values, saturation/length effects, tokenization of identifiers/acronyms/negation, empty/no-overlap cases and deterministic ties; independently specified expected values rather than duplicating implementation code.
2. All 189 unique verified payloads, source reconstruction and preserved metadata; stale hashes, modified context spans, duplicate IDs and missing/ineligible siblings fail.
3. Approved-only date boundary and HR-only results/statistics; draft-review labels; explicit identical date/mode across channels.
4. Hand-ranked RRF fixtures, rank starting at one, absent-channel contributions, ties, duplicate/mismatched records, channel errors, and no extra sibling votes.
5. Neutral score serialization and dense backward compatibility; no BM25/RRF values labeled cosine/confidence. Frozen dense scorer fixture outputs stay unchanged.
6. Complete Terraform sibling conditions, approved HR evidence, retention limitation evidence, complete-group budget exclusion and no rejected-answer publication through fake QA providers. Ordinary-query coverage stays `not_assessed`.
7. Shared query embeddings, distinct direct/expanded/post-budget coverage, parent-section matching, missing evidence and deterministic result formatting. Supplementary cases never enter frozen baseline aggregates.
8. No cloud/index mutation, provider inference, dependency/model download or backend use from the authored offline UI. BM25-only execution does not initialize MiniLM or access credentials.

Run the complete existing suite and M1.8 validator after implementation. Validate corpus/snapshot readiness before a separately approved local retrieval comparison; stop on stale state instead of rebuilding. No improvement claim until those measurements exist.

Principal risks are lexical mismatch for paraphrases, common-word/duplicated-context bias, chunk-family crowding, candidate-depth effects, score-type integration regressions, and overfitting fifteen development questions. Required sibling groups can exceed final context budgets even when direct Recall improves. None of BM25, fusion, whole-section coverage or a matching citation proves semantic answer faithfulness.
