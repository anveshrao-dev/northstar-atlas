# Section-Aware Chunking Design

> Historical engineering record. Proposals, scope limits and dated measurements
> describe the work at that time, not current setup or operational authorization.
> See the [current architecture and experiment guide](../README.md) and
> [project README](../../README.md) for the implemented system and remaining limits.

Status: Implemented for local inspection; embedding and retrieval are not implemented.

## Purpose and scope

Whole policies contain many distinct rules. Chunking creates smaller evidence
units for a later embedding stage while retaining the section, version, approval
status, and exact source needed to verify a citation. It does not turn a proposed
policy into an approved rule or determine whether a chunk fully answers a question.

The existing M2.1 loader remains unchanged and owns manifest membership, hash and
metadata validation, and approval/effective-date filtering. The chunker consumes
its verified `PolicyDocument` objects in memory. It does not discover files,
read review reports or evaluation answers, write artifacts, or call services.

## Design and implementation

The implementation follows three steps: verify the loader and corpus conventions;
test and implement section parsing, lossless splitting, and provenance; then
inspect both loader modes and rerun the corpus evaluation validator. Only
`ingestion/chunker.py`, `tests/test_chunker.py`, and this note are new files.

`chunk_document(document, *, max_chars=4000)` returns a frozen `ChunkingResult`
containing tuples of `PolicyChunk` values and explicit warning strings. The
caller must inspect warnings before sending chunks to an embedding provider.
`main()` supplies a separate CLI, preserving the M2.1 command's behavior.

The parser recognizes the corpus's column-zero `## N. Title` and
`### N.M Title` headings. It preserves their numeric identifiers as strings,
including identifiers such as `10.1`. It rejects duplicate IDs, missing or
mismatched parents, unsupported headings, unclosed code fences, and unexpected
preamble prose instead of silently assigning misleading citations. Headings
inside backtick or tilde fences are content, not new policy sections. This is
a deliberately limited parser for the verified corpus, not full CommonMark.

Each section's own text is separate from its subsections. A parent heading with
no body is retained at the beginning of its first child's source span; it does
not create a heading-only chunk. Every child also carries the parent ID and title
as metadata, including when the child's text is split. Parent **body text** is
not automatically copied into child chunks.

## Size, paragraphs, and structured content

The initial soft limit is **4,000 Python characters**, including source headings
and whitespace. It was chosen as a simple, inspectable starting point independent
of the evaluation questions. Characters require no tokenizer dependency but are
not model tokens and cannot guarantee a provider's input limit.

Sections smaller than the limit remain whole. Long prose-only sections pack
complete paragraphs in order, splitting only at blank-line paragraph boundaries.
No paragraph is subdivided or paraphrased, even when oversized. There is no
overlap, truncation, or whitespace normalization. The section heading accompanies
the first piece in the text; every piece retains its section ID and title in
metadata.

A section containing a Markdown list, pipe table, or fenced block is treated as
one conservative atomic group **with its surrounding prose**. This avoids guessing
which introductory conditions or following exceptions apply to which items.
List items with blank lines and complete tables therefore remain intact. The
tradeoff is that a very large structured section can exceed the target by a
large amount. Pipe detection is conservative and can also retain prose containing
a literal pipe as one group. An oversized paragraph or structured section is
returned intact with a warning identifying the document, section, character
range, size, and configured limit. The limit is not a hard cap.

## Data model and citations

`PolicyChunk` includes all requested fields: `chunk_id`, `document_id`, `title`,
`department`, `version`, `status`, `effective_date`, `source_path`, `content_hash`,
`section_id`, `section_title`, `parent_section`, `text`, and `chunk_index`.

Additional fields have specific purposes:

- `parent_section_title` preserves readable parent heading context;
  `parent_section` itself is the numeric ID or `None`.
- `source_start` and `source_end` are zero-based, end-exclusive character offsets
  into `PolicyDocument.content`. They support exact source reconstruction,
  debugging, and checking a piece against the original. They are not byte offsets.
- `classification`, `language`, `organization`, `policy_owner`, `review_cycle`,
  and `effective_date_text` carry forward the remaining M2.1 source metadata,
  including the raw pending-date wording and information sensitivity.

`chunk_index` is zero-based in document order, not reset for each subsection.
The derived `citation` property produces, for example,
`PLAT-001 v0.1 §6.1 (proposed)` or
`HR-001 v1.0 §4.2 (approved, synthetic)`. Multiple pieces of a subsection retain
that same section citation while receiving distinct chunk IDs. Citation metadata
must travel with the text; a heading or matching section ID alone is not proof
that a particular piece contains the required evidence.

The document title and recognized bold-label header are not policy-body chunks.
Their parsed metadata remains available on each chunk. The loader's raw document
still preserves the entire original header, including the optional Draft Date.
All text from the first numbered heading through the final footer is represented
exactly once across the ordered chunk texts. Tests verify this equality, source
offset continuity, CRLF handling, and trailing whitespace.

## Stable identities and later replacement

Each chunk ID uses the document ID, section ID, and a SHA-256 digest of a canonical
identity tuple: algorithm version (`section-v1`), document ID, document version,
verified source hash, section ID, source start/end offsets, and document chunk
index. Repeated subsection numbers in different documents do not collide.
Identical inputs and settings reproduce identical chunks and IDs. Including span
boundaries prevents different text pieces at the same index from reusing an ID
when the size limit changes. Changing the source hash changes every chunk ID for
that document, even if its version label was accidentally left unchanged.

IDs identify snapshots; they do **not** delete outdated records automatically.
The later vector-storage stage should validate and publish a complete new
document snapshot, then retire its previous chunk IDs using `document_id` and
source-hash provenance. For rechunking the same source with different settings,
compare the complete old/new ID sets and retain only the active set. Record the
algorithm version and size setting with an ingestion run. Otherwise old vectors
could remain searchable alongside replacements. No vector writes or deletion
logic are implemented in M2.2.

## Alternatives and limitations

- Fixed character windows enforce uniform sizes but can cut rules, tables, and
  exceptions apart and lose section identity.
- Token-based recursive splitting better matches an embedding input limit but
  adds a tokenizer/dependency choice and still needs explicit structural rules.
- Sentence splitting creates smaller pieces but needs reliable boundary handling
  and can separate a rule from a later qualification.
- Overlapping windows or copying whole parent bodies can improve local context,
  but duplicate evidence and consume retrieval slots. This version keeps exact,
  nonoverlapping spans with explicit parent metadata.

The current corpus's substantive sections remain whole at the initial limit.
For future long prose sections or smaller limits, qualifications in separate
paragraphs may land in different chunks. Heading metadata cannot reconstruct
those conditions by itself. Cross-section and cross-document dependencies also
remain dependencies: later retrieval must gather the required evidence and may
need to expand to neighboring pieces or parent text. Neither retrieval quality
nor answer grounding has been measured here.

## Validation results

Using Python 3.12.15 and an explicit reference date of 2026-10-22:

| Policy | Draft-review chunks |
| --- | ---: |
| HR-001 | 19 |
| IT-001 | 24 |
| PLAT-001 | 31 |
| SRE-001 | 25 |
| SEC-001 | 27 |
| COMP-001 | 25 |
| Total | 151 |

Draft-review chunk sizes are **97 / 872 / 4,179 characters** (minimum / median /
maximum). Approved-only mode returns HR-001 alone: **19 chunks**, with sizes
**97 / 253 / 299**. The 202 numbered headings remain addressable through section
and parent metadata; 51 body-free parent headings travel with their first child.

There is **one oversized-block warning**: PLAT-001 §2, source character range
`[2246:6425]`, 4,179 characters. Its ownership table and explanatory boundaries
remain together. This warning is an intentional soft-limit exception, not a
discarded block or a test failure. Approved-only mode has no oversized blocks.

All **55 unittest tests pass**: 22 existing loader tests, 19 chunker tests, and
14 existing evaluation-validator tests. The standalone M1.8 validator also
passes for all 15 questions and its pinned corpus hashes. All 40 required
evidence references resolve to emitted section IDs; this is an addressability
check, not a relevance score or tuning against evaluation answers.

Reproduce from the authorized project root:

```bash
.venv/bin/python -B -m unittest discover -s tests -v
.venv/bin/python -B scripts/validate_evaluations.py
.venv/bin/python -B -m northstar_atlas.ingestion.chunker --mode draft_review --reference-date 2026-10-22
.venv/bin/python -B -m northstar_atlas.ingestion.chunker --mode approved_only --reference-date 2026-10-22
```

The CLI prints counts, section citations, sizes, and warnings without full policy
text. `--max-chars` changes the soft limit; the default mode remains approved-only.
Warnings are on stderr with successful exit status because content is preserved;
invalid sources or settings produce a nonzero exit status.

Before embedding, inspect the flagged table section, small chunks, split-section
qualifiers under any revised limit, source status, and parent context. Choose an
embedding model and measure its actual token limits in the later authorized
stage; do not blindly truncate oversized blocks. Persist provenance and metadata
alongside vectors and keep proposed-policy filtering explicit. No policies,
manifest hashes, dependencies, or existing loader behavior are changed by M2.2.
