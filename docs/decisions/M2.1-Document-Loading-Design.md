## 1. Purpose and Design

The loader turns a controlled collection of Markdown files into verified Python
objects. It establishes which files belong to this corpus, confirms their bytes
match the manifest, checks their metadata, and preserves the text for later work.
It does not split text, embed it, search it, or generate answers.

The flow is:

```text
repository root
  -> fixed corpus manifest
  -> schema, paths, IDs, statuses, and dates
  -> each listed file: bytes -> SHA-256 check -> UTF-8 decode -> metadata check
  -> complete verified document list
  -> requested status/effective-date filter
  -> PolicyDocument objects
```

This resembles a CI artifact-validation stage: check the declared inputs and their
digests before permitting downstream processing. It is deliberately separate from
the later retrieval engine, so the same verified objects can eventually feed Chroma,
Pinecone, or another storage implementation without changing the source rules.

All manifest-listed files are validated before filtering. A corrupted draft fails
the load even in approved-only mode; the result is never a silently partial corpus.
This makes corpus integrity independent of the selected view. The alternative,
validating only included files, would reduce reads but could hide a broken snapshot.

| This document | Design, usage, implementation rationale, and validation record |

`load_manifest(project_root)` reads the fixed `data/corpus_manifest.json` and returns
validated entry dictionaries in manifest order. These are JSON input records, not
yet loaded document objects. Schema v1 requires the existing manifest fields and
the ten existing per-policy fields. Duplicate JSON keys, duplicate document IDs,
malformed types, unknown statuses, invalid dates, and invalid digests fail clearly.

`load_documents(project_root, *, mode="approved_only", reference_date=None)` verifies
files and returns `list[PolicyDocument]` in manifest order after filtering. The `*`
makes mode and date keyword arguments, so a call's intent is readable. No document
IDs or corpus count are hardcoded: this manifest currently supplies six files.

`PolicyDocument` is a frozen dataclass with:

- `document_id`, `title`, `department`, `version`, and original `status`.
- `effective_date` as `datetime.date | None`, plus `effective_date_text` preserving
  the source's pending-date wording.
- `classification`, `language`, `organization`, `policy_owner`, and `review_cycle`.
- `source_path` as a repository-relative `Path`, and the verified `content_hash`.
- `content` containing the full, unchanged decoded Markdown.

Manifest fields are checked against the heading and bold-label source metadata.
Organization, policy owner, review cycle, and original effective-date text come
from the source header. Draft Date, when present, is validated as a date but is
never used as effectiveness; it also remains available in the unchanged content.

`DocumentLoadError` is the shared exception for invalid or unreadable corpus input.
Library callers can catch it. The CLI reports a concise error on stderr and exits
1 without dumping raw input or returning partial document summaries. Argument
errors, such as an invalid mode/date flag, use argparse's exit status 2.

Example library use after verifying the authorized checkout as the working directory:

```python
from datetime import date
from pathlib import Path

from northstar_atlas.ingestion.document_loader import load_documents

root = Path.cwd().resolve()
documents = load_documents(
    root,
    mode='draft_review',
    reference_date=date(2026, 10, 22),
)
for document in documents:
    print(document.document_id, document.status, len(document.content))
```

## 3. Manifest Membership and Path Boundaries

The [manifest](../../data/corpus_manifest.json) is the source allowlist, analogous
to a deployment inventory. The loader does not scan directories recursively or
follow related-policy references to discover more files. Unlisted files are ignored,
including extra Markdown placed in the policy directory.

Schema v1's source path convention is `data/policies/<document_id>.md`. The loader
rejects absolute paths, traversal paths, and mislisted review/evaluation paths.
It resolves the manifest and each source path and verifies that the resolved file
stays inside the supplied root, including when symlinks are involved. Missing files,
directories in place of files, unreadable files, and unresolvable paths are errors.
It reads each source's bytes once for hashing and decoding.

The library takes an explicit root rather than hardcoding this Mac's username.
That root is the caller-supplied boundary, not an untrusted manifest setting. In
this task every command uses the authorized checkout; test roots are isolated
copies inside its `.local/tmp/`. The CLI defaults to this editable source checkout
and accepts `--project-root` for an explicit checkout or local test fixture.

These checks are application-level path validation, not an OS sandbox or protection
against a hostile process concurrently replacing filesystem entries. Treat corpus
updates as controlled changes. The loader never writes files, repairs metadata,
updates hashes, or changes policy status.

## 4. SHA-256 and Exact Content Preservation

`Path.read_bytes()` returns the actual file bytes. `hashlib.sha256(raw).hexdigest()`
computes their lowercase 64-character digest, which must equal the manifest value.
A changed space, line ending, or character changes the expected bytes and normally
the digest. A mismatch stops the load; it does not silently refresh the manifest.

Only after the hash matches does `raw.decode('utf-8')` produce a Python string.
Decoding the same byte buffer avoids a second read of potentially different data.
It also avoids text-mode newline conversion: CRLF, LF, trailing spaces, and trailing
newlines remain unchanged in `content`. Metadata parsing examines a separate view
of that string and does not rewrite it. Tests verify UTF-8 round-trip byte equality,
including a CRLF fixture, and reject invalid UTF-8 even with a matching digest.

A hash establishes consistency with a chosen manifest, not policy truth, author
identity, or publication approval. A deliberately updated source and manifest need
human review. The separate M1.8 validator also checks the evaluation dataset's
manifest pin, which will catch a changed experimental snapshot even when all newly
recorded file hashes agree. This loader consumes the current manifest rather than
embedding an evaluation-specific pin in application code.

## 5. Approval and Effectiveness Rules

| Mode | Inclusion rule |
| --- | --- |
| approved_only | Status exactly `Approved (Synthetic)`, with a valid effective date on or before the reference date, inclusive |
| draft_review | Both supported statuses: `Approved (Synthetic)` and `Draft — Proposed (Synthetic)`; retains future approved policies as review material as well as drafts |

Approved entries require a real ISO `YYYY-MM-DD` calendar date matching the source
header. Draft entries require JSON null and one of the current pending-date header
phrases. They become Python `None`, never a draft date or guessed effective date.
The raw header wording remains in `effective_date_text` and in `content`. Unknown
statuses are errors; they are not guessed into either category.

Callers should supply `reference_date=date(...)` for reproducible tests and runs.
When omitted, the loader uses today's **UTC calendar date**, not the machine's
local calendar. The CLI displays the date it actually used. At this validation's
UTC reference date, 2026-10-22, HR-001's 2026-10-01 effective date qualifies; all
five drafts remain excluded in approved-only mode. Before 2026-10-01, approved-only
returns an empty list; on that date it includes HR-001. Draft-review still includes
all six. Filtering reads status/date values, not an approved-document ID list.

Dates are day-level metadata, not activation timestamps. There is no expiry,
withdrawal, supersession, or precedence field in this manifest. Consequently the
loader does not invent those semantics. Policy-effective dates are also separate
from employee termination times described inside HR policy text.

## 6. Why Reviews and Policies Stay Separate

Engineering reviews contain design alternatives, historical snapshots, proposed
corrections, and unanswered questions. Evaluation files contain answer keys.
Treating these as policy evidence could promote an unapproved suggestion, cite an
obsolete dependency state, or leak an expected answer into retrieval.

Only explicit manifest policy entries are loaded. There is no recursive ingestion
of `docs/decisions/`, `evaluations/`, README files, `AGENTS.md`, logs, or temporary
files. Tests place invalid unrelated files in these locations and confirm they are
not read. Draft policies are still policies for review mode, but their proposed
status remains attached to their text.

## 7. Implementation Rationale

| Concept | What it does here | DevOps analogy |
| --- | --- | --- |
| Dataclass | Generates the initializer and useful comparison/representation behavior for named document fields; `frozen=True` prevents accidental field reassignment | A typed artifact record carrying payload, version, provenance, and deployment eligibility together |
| Type hints | Describe interfaces such as `list[PolicyDocument]`, a `date` or `None`, and the two permitted mode literals | A documented module or pipeline input contract; hints help tools but do not validate untrusted data at runtime |
| pathlib | Represents paths, joins them, resolves symlinks, and checks directory containment | Explicit artifact paths and workspace boundaries instead of fragile string concatenation |
| JSON loading | Converts the manifest into dictionaries/lists, then validates the actual shape and values | Reading a deployment inventory is separate from validating that it is well formed and usable |
| File hashing | Verifies the bytes against the recorded digest before interpreting them | Comparing a downloaded artifact or image digest with the expected build output |
| Exception handling | Stops an invalid load and lets library callers or the CLI report failure consistently | A failed validation stage blocks downstream work rather than passing incomplete artifacts onward |
| Keyword arguments and small functions | Make `mode=` and `reference_date=` explicit; isolate path, manifest, source, and filtering responsibilities | Named pipeline inputs and focused validation steps that are easier to inspect and test |

A bare string would lose the connection between content and its source, approval,
version, and hash. A dictionary can work but is easy to misspell or mutate. A frozen
dataclass makes the document contract visible without a validation framework or
inheritance hierarchy. Runtime checks are still needed because JSON can contain
wrong types regardless of Python annotations.

The M1.8 validation script remains unchanged. It is a standalone benchmark validator;
the application loader does not import a script from `scripts/` or depend on the
evaluation schema. Some small input checks intentionally overlap. A shared schema
utility could be considered later if maintaining both becomes burdensome, rather
than coupling the loader to the evaluation tool.

## 8. CLI Usage and Output

Use the already synchronized uv-managed `.venv` directly; this needs no sync,
downloads, package installation, or change to `pyproject.toml`:

```bash
pwd
.venv/bin/python -B -m northstar_atlas.ingestion --mode draft_review --reference-date 2026-10-22
.venv/bin/python -B -m northstar_atlas.ingestion --mode approved_only --reference-date 2026-10-22
```

Omit `--reference-date` to use today UTC. The module command uses the installed
editable package; no `PYTHONPATH` modification or `sys.path` workaround is needed.
The CLI reports document ID, title, department, version, original status, Unicode
character count, and SHA-256 PASS. It prints no full policy body. PASS is shown only
after all source validation succeeds; an integrity failure returns no partial rows.

The default root assumes the current editable source layout. For a future wheel
installation or another checkout, pass `--project-root` explicitly; the corpus is
not bundled into the Python package. This is local inspection, not a service API.

## 10. Limits, Alternatives, and Chunking Interface

The parser deliberately supports the current schema-v1 manifest and Markdown
heading/bold-label metadata format. It is not a general Markdown parser or a
semantic policy validator. It does not determine whether a policy is well written,
resolve governance gaps, or verify that a synthetic approval marker represents an
actual approval process. New statuses, format conventions, lifecycle fields, or
manifest schema changes require an explicit design update.

All files are read into memory; this is appropriate for six small policies. A large
corpus might need streaming, caching, or incremental validation. Those features
would add complexity and are not needed here. JSON Schema/Pydantic or a framework
loader could provide richer validation/integration later, but would add dependencies
without improving the loader's core contract. Recursive scanning would be
simpler to start but would weaken reproducible membership and source separation.

Section-aware document chunking can consume these objects and split their
content at stable section boundaries. Each future chunk should retain document ID,
version, status, effective date, source path/hash, and its section context; conditions
and exceptions must stay with their rules. The full verified document is the input
contract. Chunking must not rewrite policy meaning or turn a draft into an approved
rule. No chunker, embeddings, vector store, retrieval, generation, or LangGraph
component is implemented in M2.1.
