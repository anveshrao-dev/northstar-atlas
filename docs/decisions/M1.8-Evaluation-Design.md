## 1. Purpose and Source Boundary

Define expected behavior before choosing a retrieval engine or seeing generated
answers. This gives later experiments a common benchmark for retrieval coverage,
authority handling, faithful synthesis, clarification, and grounded abstention.

The [manifest](../../data/corpus_manifest.json) is the authoritative file list
for this experiment. All six listed files were read and their raw-byte SHA-256
hashes verified before preparing questions. The reconciled policies supply
expected-answer evidence. The [M1.7 consistency report](M1.7-Corpus-Consistency-Report.md)
supplies engineering context only; neither it nor historical reviews are policy
evidence or retrieval candidates.

HR-001 remains v1.0, Approved (Synthetic). IT/PLAT/SRE/SEC/COMP remain v0.1,
Draft — Proposed (Synthetic), with no effective dates. Project acceptance does
not publish them. Corpus gaps remain gaps; this task changes no policy.

## 2. Dataset and Design Decisions

The [dataset](../../evaluations/questions.json) has exactly fifteen questions:

| Category | Count | Mode | Expected behavior |
| --- | --- | --- | --- |
| A — Direct HR lookup | 3 | approved_only | answer |
| B — Cross-document retrieval | 6 | draft_review | answer |
| C — Ambiguous queries | 3 | draft_review | clarify |
| D — Unsupported questions | 3 | draft_review | abstain |

Stable IDs EVAL-001 through EVAL-015 identify cases without encoding a model,
vendor, or chunking strategy. Category B receives six cases to exercise each
specified enterprise scenario. Categories C and D distinguish missing user
context from missing corpus authority. This distribution is deliberate coverage,
not an estimate of real user-question frequency.

JSON is portable and supports typed evidence/qualifier arrays. Markdown alone
would be easy to read but harder to validate consistently; a spreadsheet would
add an unnecessary format and tooling dependency. No additional package is needed.

Each evidence item is one document/section pair. Required units are conjunctive:
all contribute to full retrieval coverage. There are forty required units across
the questions, with one to five per question. Repeated units across different
questions count separately in per-question scoring. No alternative evidence is
designated in this release; the optional mapping format is defined in the
[evaluation README](../../evaluations/README.md).

The dataset pins the SHA-256 of the complete manifest bytes. This prevents a later
manifest-and-policy update from silently changing the experiment underneath its
labels. Version 0.1 is a reviewable benchmark version, not policy approval.
After an intentional corpus change, review affected questions/evidence and revise
the dataset version and pin together; do not merely refresh the hash to pass.

## 3. Expected Evidence Methodology

Read the whole policy, then select the smallest useful sections supporting the
question's required decisions and conditions. Evidence must establish the actor,
authority, action, scope, and exceptions needed for the expected answer. Related
policy lists and technology mentions are not sufficient supporting evidence.

For inherited lifecycle rules, cite HR directly. For draft controls, attach
proposed status to expected answers and future retrieved chunks. Cross-document
answers must not use one source's authority to promote another source's proposal.

Expected summaries are semantic answer guides, not exact-match target strings.
Required qualifiers and forbidden inferences identify errors a plausible-sounding
paraphrase could hide. Structural validation can check a reference exists but
cannot prove its relevance or an answer's faithfulness; these require content review.

The README fixes section-unit Recall@5, full-evidence coverage, authority leakage,
claim-level faithfulness, citation correctness/completeness, and behavior scoring.
Five retrieved chunks are the cutoff; they are not five document titles. A chunk
can satisfy more than one section unit only if it actually contains the supporting
text and conditions. Repeated chunks cannot earn repeated credit for one unit.

## 5. Unsupported and Ambiguous Cases

EVAL-010 needs hosting/component and production-impact context; EVAL-011 needs
identity, target, permission, purpose, and duration context; EVAL-012 needs the
current window and a recorded authorized extension decision. A good clarification
is specific and still explains the applicable conditional boundaries.

EVAL-013 cannot supply an exact approved retention period. EVAL-014 cannot supply
an exact approved MFA method or fixed credential-rotation interval. EVAL-015
cannot supply a detailed approved GCP deployment runbook. Their correct behavior
is grounded abstention from the unavailable claim, accompanied by supported
proposals and the unresolved decision. A bare refusal discards useful evidence;
an invented value or procedure fails even if surrounded by correct generalities.

Missing context can sometimes be supplied by a user; missing policy approval
cannot be supplied by guessing. Do not use general industry practice, vendor
documentation, or model memory as company-policy evidence for these cases.

## 6. Planned Comparisons

All comparisons are future experiments. No engine, model, API, or service is run
in M1.8.

| Comparison | Hold constant | Vary and measure |
| --- | --- | --- |
| Chroma versus Pinecone | Exact corpus/dataset hashes, chunk IDs and text, embedding model/version/dimensions, queries, mode filters, top-k, and scoring rules | Backend/index configuration; record Recall@5, complete-evidence coverage, filter correctness, latency and separately reported resource/cost context |
| Dense versus hybrid search | Corpus snapshot, question set, eligible source set, evaluation units, result cutoff, and comparable candidate budget | Dense-only ranking versus combined dense/lexical ranking; document lexical preprocessing, fusion method/weights, and score normalization; check IDs/acronyms as well as semantic paraphrases |
| Without versus with reranking | Same frozen candidate pool per question, mode filter, corpus snapshot, and final five-result cutoff | Reranker/model version and ranking order; report pre/post Recall@5, complete coverage, latency, and candidates unavailable to the reranker |

Record seeds where supported, configuration versions, hardware/network context,
and repeated timing conditions. Align similarity metric/normalization where
possible; disclose unavoidable differences rather than attributing every result
to the backend. Reranking cannot recover a missing candidate. Apply source-mode
filters before candidate generation and retain them through later stages.

For answer comparisons, hold the retrieved context, prompt/version, generation
model/version, parameters, and citation format constant when testing generation.
When testing the whole pipeline, record both retrieval and answer outcomes so a
retrieval miss is distinguishable from unfaithful synthesis of correct evidence.
Store future generated results and caches inside ignored `.local/`.

## 7. Limitations and Alternatives

Fifteen hand-authored synthetic questions are a development smoke benchmark.
They do not establish broad statistical reliability, real enterprise distribution,
production safety, or superiority of one engine. A single case changes overall
behavior accuracy by about 6.7 percentage points; within a three-case category,
it changes accuracy by about 33.3 points. Always show counts and per-question
outcomes alongside averages.

Questions share policies and concepts, so observations are not independent.
This is a visible development set, not a hidden test set: tuning on it risks
overfitting. Later work should add independently reviewed paraphrases, held-out
questions, harder distractors, longer documents, multilingual cases, permission
boundaries, and adversarial queries before broad claims.

Section-based evidence labels favor traceability but do not fully judge chunk
boundaries or all valid paraphrases. The currently empty alternative lists may
penalize a genuinely equivalent source; review and version new alternatives
before comparison, never opportunistically after seeing a favored system's result.
Recall alone does not measure rank quality, answer completeness, or irrelevant
context. Any later MRR/nDCG, precision, or larger-k analysis must be labeled
separately rather than replacing the fixed Recall@5 benchmark silently.

Five sources are drafts. Experiments must label review-mode answers and must not
demonstrate proposed controls as effective operational policy.

## 8. Implementation and Validation Plan

1. Verify source hashes and read the manifest-listed policies and M1.7 context.
2. Author exactly fifteen questions with verified evidence, required qualifiers,
   forbidden claims, and source-mode boundaries.
3. Write standard-library validator tests using isolated fixtures under
   `.local/tmp/`; exercise valid input and rejected malformed or unsafe labels.
4. Implement `scripts/validate_evaluations.py` with no external dependencies.
5. Run it with the existing Python 3.12 environment, run the tests, review expected
   answers against source text, and compare source/Git hashes to the baseline.

The validator resolves the project from its script location, checks manifest
integrity and the dataset pin, validates the schema/distribution/evidence/modes,
and exits nonzero with readable errors. It reads data and never repairs or writes
sources. Reproducible commands and the schema are documented in the README.

A small standard-library regression test file accompanies the validator because
accepting an invalid section or draft evidence in approved-only mode would produce
misleading future evaluation results. It tests the CLI using copied local fixtures;
it does not run model evaluations or alter the original corpus.

## 9. Prerequisites for Retrieval Experiments

Retrieval experiments depend on an accepted dataset and scoring contract, passing
structural and integrity checks, explicit mode/status handling and source isolation,
and review of the relevant open corpus decisions.

Operational governance gaps do not need invented resolutions for a synthetic
draft-review experiment; they must remain explicit and tested. Retrieval must not treat
that experiment as policy publication or production authorization. Approve any new
dependency separately after its purpose and alternatives are explained. No
LangChain, Chroma, Pinecone, ingestion, embeddings, or application work starts here.
